## 背景
清算对账发现分账合计和订单金额对不上：0.10 元订单按 0.3333/0.3333/0.3334 分账合计 0.09；1999.99 元订单合计 2000.00。 · 场景：缺陷修复

## yeeHarness 交付卡
### 归一化 / 需求卡片
| 维度 | 内容 |
|---|---|
| EXPECTED | 各方分账金额之和严格等于订单金额（AGENTS.md 分账不变量） |
| SYMPTOM | 0.10 → 合计 0.09（少 1 分）；1999.99 → 合计 2000.00（多 1 分） |
| TRIGGER | 任意比例下逐方舍入出现进位/舍去不抵消，可稳定复现 |
| RECENT_CHANGE | 仅初始提交 e859cba，缺陷自始存在 |

### 根因与证据
- 断裂点：`SplitCalculator.split`
- 根因：(1) 金额转 `double` 计算并用 `Math.round` 舍入（违反 P-001）；(2) 每一方独立舍入到分，没有任何一方承接尾差，舍入误差直接留在合计里。
- 证据：复现测试 `sharesAddUpToOrderAmountWhenRoundingLosesACent` / `...GainsACent` 在修复前失败，实际值分别为 `0.09` 和 `2000.00`，与对账报告的数字一致。0.10×0.3333=0.03333→0.03（3 方均为 0.03）；1999.99×0.3333=666.5967→666.60，×0.3334=666.7967→666.80。
- 已排除：`Money.requireValid` 与 `SplitRule`/`SplitShare` 的校验没有问题，误差只来自计算和舍入。

### 影响面评估
- 直接改动：`split/SplitCalculator.java`；方法签名与返回结构不变。
- 上游：仓库内没有其他生产代码调用 `SplitCalculator`。
- 金额变化：除最后一方外，各方金额与原来逐方 HALF_UP 的结果一致；最后一方的金额会差 ±1 分（承接尾差）。
- 行为变化：比例合计 ≠ 1 时抛 `IllegalArgumentException`（原来会静默产生差额）；订单金额小到前面各方舍入后已超过订单金额、最后一方会变成负数时，抛 `IllegalArgumentException`。
- 存量数据：本次不修复历史分账记录。

### Delta（MODIFIED / ADDED / UNCHANGED）
- MODIFIED `SplitCalculator.split`：全程使用 BigDecimal；除最后一方外各方按 `HALF_UP` 舍入到分；最后一方 = 订单金额 − 前面各方之和；新增比例合计 = 1 校验和最后一方非负校验；返回不可变 List。
- ADDED `SplitCalculatorTest`：2 个复现测试，尾差归属、0~1000 元每隔 7 分逐一检查合计、单方分账、比例合计 ≠ 1、最后一方为负 各 1 个测试。

- UNCHANGED：`SplitRule`、`SplitShare`、`Money`、对账与回调模块。

### 假设
- 非最后一方的舍入方式沿用原来的四舍五入（HALF_UP，与原 `Math.round` 对正数的结果一致），各方金额尽量不变。
- 类注释写明“shares always add up to the order amount”，比例合计 ≠ 1 时这个约定本来就无法成立，所以改为直接报错。如果业务上存在比例合计 < 1、剩余部分留给平台的场景，需要另提需求。
- 极小金额下最后一方会变成负数的情况，同样直接报错，不输出负的分账金额。
- 不修复存量分账数据。
