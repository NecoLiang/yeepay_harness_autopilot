# 演示脚本（3–5 分钟，全程在飞书完成）

预备：飞书演示群、面板（`http://127.0.0.1:3082`，带 token 的地址见启动日志）、演示仓库 PR 页，三个窗口并排。

## 镜头 1：在 IM 里一句话提需求（30 秒）

在演示群里发：

> @yeeHarness助手 清算对账发现分账合计和订单金额对不上：0.10 元的订单三方按 0.3333/0.3333/0.3334 分账，合计只有 0.09；1999.99 的订单合计却是 2000.00。帮忙修一下。

讲解：需求方不需要知道代码在哪，也不需要打开 IDE。

## 镜头 2：只确认一次（30 秒）

机器人在原话题里回复一次，写明场景和预期结果，例如「按缺陷修复流程处理：让分账合计与订单金额严格一致，完成后发 PR」。

切到面板：Overview 出现工单，状态为 Working。讲解：之后它不发进度，不占用大家的注意力。

## 镜头 3：资金取舍问人，而且只问一个问题（45 秒）

机器人在话题里问出一个资金决策，例如「尾差（1 分）分给哪一方？A. 最后一方（推荐）B. 平台方 C. 比例最大的一方」。

回复：`A`。

讲解：分账尾差归谁会影响资金结果，scope 规定这类问题必须问人。其他信息它都自己查了，包括 git log、复现测试和根因。

## 镜头 4：门禁是 ready 的唯一依据（60 秒）

打开 PR，展示：
- 交付卡：归一化四格、根因与证据（double 计算并逐份四舍五入）、影响面、Delta、决策记录（尾差 → A）
- 交付门禁报告：P-001 等规则检查通过，测试通过
- 先写的复现测试：0.10 / 1999.99 / 0.01 三个金额合计等于订单金额
- GitHub CI 里同一个门禁再跑一遍

如果 agent 第一版用了 double，或者 `setScale` 没写舍入模式，门禁会把它拦下，agent 自行修正后才会报告 ready。PR 的提交历史里能看到这个过程。

## 镜头 5：在飞书里交付，并附带进化邀请（15 秒）

机器人在原话题里回复：「分账合计现在与订单金额严格一致，[PR #1](…) 可以评审了。另：本次可沉淀为业务规约 R-001『分账尾差必须显式分配』，回复『同意 R-001』即纳入门禁。」

讲解：规则审批不会阻塞交付，PR 已经可以评审。

## 镜头 6：进化闭环，审批即生效（60 秒）

回复：`同意 R-001`。这条消息会经订阅回到同一个工单，不需要重新 @机器人。

PR 新增一个提交，包含两处修改：`.yeeharness/gate-rules.json` 加入 R-001，`AGENTS.md` 业务规约表加了一行。PR 评论里出现进化播报块，以及新规则对旧写法的命中证据。

讲解：一次踩坑，全团队免疫，而且整个过程都在 IM 里完成。

## 镜头 7：数据（30 秒）

```sh
python scripts/collect_metrics.py && python scripts/render_report.py
open site/index.html
```

展示门禁基准（12/12 拦截、0/9 误拦）和实跑数据：需求到可评审 PR 的时长、每单机器人发言和人工发言条数。

预期：路由到「旧需求迭代」场景，PR 里带回归保护清单。
